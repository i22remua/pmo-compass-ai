# Security audit

Audit date: 2026-09-29. Scope: tracked application source, Firebase rules, tests, deployment configuration and documentation at the security-hardening change. This is a code review and test record, not a penetration test or compliance certification.

## Summary

No supported critical vulnerability was found. The existing design already used owner-scoped Firestore rules, immutable ownership fields, verified Firebase tokens for private API routes, backend-only AI keys, strict Pydantic input models, bounded bodies, safe error messages, provider timeouts, Markdown without raw HTML and offline fallback. The findings below describe concrete gaps observed in that implementation.

| Severity | Risk and component | Realistic attack scenario | Protection found before change | Mitigation and status |
| --- | --- | --- | --- | --- |
| HIGH | App Check was absent from Firebase/browser and custom API requests. | Automated clients can call public generation from outside the intended web app and consume free quota; stolen Firebase browser configuration can be reused. | Authentication, Firestore rules and process-local rate limits; these do not attest the app. | reCAPTCHA Enterprise App Check client support, custom API token forwarding and backend monitor/enforce modes implemented. **Source complete; production key, monitoring and enforcement remain manual.** |
| HIGH | Account deletion did not remove the Auth account and all owned data. | A user could not exercise complete deletion and stale owned records could remain after an interrupted project delete. | Per-project retryable deletion and Firestore owner checks. | Export, reauthentication, owner-scoped orphan cleanup, profile deletion and Firebase Auth deletion implemented. Emulator/browser verification is required before checking the release item. |
| MEDIUM | Next.js sent only three basic headers; no CSP, HSTS or Permissions Policy. | An injection bug or unsafe third-party content would have fewer browser containment controls; pages could rely only on legacy frame blocking. | React escaping, Markdown `skipHtml`, `X-Frame-Options`, `nosniff`, referrer policy. | Per-request nonce CSP plus HSTS and Permissions Policy implemented; production header script added. |
| MEDIUM | Provider prompts serialized operational fields and persistent source/record IDs. | An external AI provider could receive identifiers unrelated to the requested analysis, increasing disclosure impact. | No Firebase uid, email or token was part of the request model; explicit offline consent existed for saved sources. | `minimal_ai_context` now excludes persistent IDs, account data, privacy flags and fallback controls; browser references are request-scoped; tests added. |
| MEDIUM | API logs had safe provider errors but no uniform request metadata policy. | Future exception logging could include raw exceptions or developers could log request bodies to diagnose failures. | No body logging was found; provider errors logged only provider/status or stable codes. | Request middleware now logs generated request ID, endpoint, status and duration only; generic exceptions log type, not message or input. |
| MEDIUM | Rate limits are in process memory. | Requests distributed over multiple serverless instances can exceed the nominal limit. | Per-IP minute limits, per-uid/IP free quotas, provider quotas and offline degradation. | Limitation documented accurately; App Check adds an independent abuse signal. A shared durable limiter remains future work if traffic warrants it. |
| MEDIUM | No repository-wide standalone secret scan command or Python dependency audit in CI. | A credential could be committed in a new file, or a known Python package vulnerability could go unnoticed. | Release check already detected common tokens, forbidden env files, private keys and staged secrets; npm audit ran in CI. | Dedicated `security:secrets`, `pip-audit` and CI steps added without automatic breaking upgrades. |
| MEDIUM | Password reset and email verification existed in Firebase but were not exposed by the UI. | Users could remain unverified or be unable to recover access through the product UI. | Firebase email/password sign-in and logout; expired tokens rejected by backend. | Generic password-reset flow and verification email actions implemented. Enumeration-resistant copy is used. Firebase Console email-enumeration protection remains an operator setting. |
| LOW | CORS was configured from environment but production-specific validation was absent. | A mistaken `*` or HTTP origin in production configuration could widen browser access. | Explicit local defaults; Starlette did not reflect arbitrary origins; methods and headers were restricted. | Production settings now reject wildcard and non-HTTPS origins; negative tests added. |
| LOW | Markdown relied on the library's default URL handling. | A regression or configuration change could allow a `javascript:` link even though raw HTML is skipped. | `react-markdown` with `skipHtml`; images removed; links used `noopener noreferrer`. | Explicit protocol allowlist added for HTTP, HTTPS, mail and fragment links; malicious content tests cover scripts, iframe, event handlers and JavaScript URLs. |
| LOW | Oversized bodies were rejected only while reading the stream. | A caller could force unnecessary body reads up to the limit repeatedly. | Streaming 256 KB limit and Pydantic per-field/array constraints. | Early `Content-Length` rejection added while retaining streamed-size enforcement for chunked bodies. |
| INFORMATIONAL | Browser local workspace is stored as plaintext localStorage. | Anyone with access to the browser profile or injected same-origin script can read local projects. | Local mode is labelled device-local and separated from Firebase storage. | Security page and data documentation clarify the model. Sensitive shared-device work should use an authenticated account and normal device controls. |
| INFORMATIONAL | Firestore encryption is server-side, not end-to-end. | Google/Firebase services process plaintext under their service boundary; sending context to AI adds another processor. | TLS, Firestore encryption at rest, owner rules and offline AI choice. | Accurate encryption documentation added. Optional AES-GCM storage was analysed and deferred because query, recovery, migration and AI plaintext requirements make a safe rollout a separate product project. |
| INFORMATIONAL | Public generation endpoints intentionally require no account. | Anonymous users can submit their own project snapshot for generation. | They cannot read Firestore, are rate-limited, validate input and can fall back offline. | Endpoint matrix and limitations documented; App Check rollout covers the public client without misrepresenting it as user authorization. |

## Firestore result

The rules validate allowed keys, value types and lengths; make `ownerId`, `projectId` and `createdAt` immutable where appropriate; require an active owner-matched parent for child creation; permit owner cleanup of orphans; and finish with a recursive deny-all. Queries in the application include `ownerId == uid`. Emulator tests separately cover anonymous denial, cross-user CRUD, forged ownership, child moves, malformed data, unexpected collections and retryable deletion.

## Secrets result

No tracked `.env`, service-account file, private certificate or provider credential was found by the repository scans. Firebase browser configuration is public by design; Firebase service-account JSON and AI provider keys remain server-only. Pattern scanning cannot prove that Git history or external deployment settings have never contained a secret, so operators must still review GitHub and Vercel secret inventories and rotate any credential suspected of exposure.
